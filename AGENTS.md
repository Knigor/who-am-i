# Правила работы с проектом

## О проекте

Небольшой персональный сайт-портфолио.
Стек: Vue 3, TypeScript, Vite, Vue Router, Tailwind CSS 4,
shadcn-vue / Reka UI, vue-i18n.
Менеджер пакетов — Bun.
Тестовый стек: Vitest, Vue Testing Library, user-event и jsdom.

Предпочитать простые решения, соответствующие размеру проекта.
Не внедрять FSD, дополнительные архитектурные слои или библиотеки
без конкретной необходимости.

## Формат взаимодействия

- Общаться на русском языке.
- По умолчанию работать в режиме обучения: пользователь пишет код,
  агент объясняет, предлагает примеры и проверяет результат.
- Перед реализацией объяснять назначение изменения, место в проекте
  и способ проверки.
- Разбирать работу небольшими последовательными шагами.
- Просьба «проверь» означает ревью, а не разрешение исправлять файлы.
- Читать файлы и исследовать проект можно самостоятельно.
- Изменять файлы и устанавливать зависимости только при явной
  просьбе пользователя выполнить эти действия.
- Если изменения уже разрешены, не запрашивать повторное разрешение
  на каждый файл в пределах согласованной задачи.
- Не выполнять commit, push, создание тегов и публикацию
  без соответствующей просьбы пользователя.

## Перед началом работы

- Сначала изучить относящиеся к задаче файлы и существующие решения.
- Проверять команды и зависимости по package.json.
- Не предполагать наличие компонентов, библиотек или скриптов.
- При сомнениях в API сверяться с официальной документацией
  с учётом установленной версии.
- Не затрагивать несвязанный код и изменения пользователя.

## Структура проекта

- src/pages — компоненты страниц.
- src/components — компоненты приложения.
- src/components/ui — базовые компоненты shadcn-vue.
- src/router — маршруты.
- src/i18n — настройка локализации и общие переводы.
- src/assets/style.css — глобальные стили и токены темы.
- src/lib — общие вспомогательные функции.

Создавать новые каталоги и абстракции при появлении реальной
потребности. Не выносить каждую небольшую функцию в отдельный модуль.

## Vue и TypeScript

- Использовать Composition API и <script setup lang="ts">.
- В Vue-компонентах располагать <template> первым, а <script> — после него.
- Не добавлять комментарии в код. Объяснения давать в чате.
- Типизировать props, emits и данные на границах приложения.
- Не скрывать ошибки типов через any, @ts-ignore или необоснованные
  утверждения типов.
- Использовать реактивность Vue для состояния интерфейса.
- Выносить повторяющуюся логику в composables, когда это упрощает код.
- Следовать существующему ESLint-конфигу.
- Не добавлять глобальное хранилище для локального состояния компонента.

## Группировка импортов

Разделять импорты на смысловые блоки в следующем порядке:

1. Типы — отдельные import type перед всеми импортами значений.
2. Сторонние библиотеки и API фреймворка.
3. Компоненты, включая UI-компоненты и иконки.
4. Composables.
5. Stores.
6. Остальные модули: утилиты, конфигурация, константы и ресурсы.
7. Enum — последняя группа импортов значений.

- Между группами оставлять одну пустую строку; внутри группы держать
  связанные импорты рядом. Не добавлять комментарии-разделители.
- Не смешивать типы и значения в одном import: использовать отдельный import type.
- В блоке типов также группировать импорты по назначению и разделять группы
  пустой строкой: сторонние типы, компоненты, composables, stores, остальные, enum.
- Группировать по назначению: composables из сторонних библиотек помещать
  в блок composables, а компоненты и иконки из библиотек — в блок компонентов.
- Enum, используемый только как тип, импортировать через import type
  в конце блока типов; enum, используемый как значение, — в самом конце импортов.
- Не менять порядок импортов с побочными эффектами, если от него зависит поведение.

ESLint проверяет группы локальным правилом local/import-groups.
Composables определяются по каталогу composables или имени use с заглавной
буквой после него; stores — по каталогу store/stores или имени use…Store.
Enum распознаются по каталогу enum/enums или окончанию Enum в имени импорта.
При импорте с переименованием учитывается исходное имя.
Компоненты распознаются по .vue, каталогу components, @lucide/vue
и именам с заглавной буквы из Vue, Vue Router и Reka UI.
Для нового источника компонентов при необходимости дополнять правило.
Импорты без привязок, например import './style.css', разделяют независимые
блоки сортировки: ESLint не переносит другие импорты через них.
Автоисправление сохраняет порядок внутри групп. Смешанные группы в одной
строке нужно разделять вручную; блоки с комментариями автоматически не перемещаются.

## Компоненты и доступность

- Использовать существующие компоненты shadcn-vue.
- Перед добавлением компонента проверять src/components/ui.
- Использовать только иконки из установленного @lucide/vue.
- Не добавлять SVG-спрайты, собственные SVG-иконки и другие библиотеки иконок.
- Цвет иконок наследовать через currentColor; размер задавать на компоненте.
- Декоративные иконки скрывать от скринридеров через aria-hidden="true".
  Для самостоятельной смысловой иконки задавать role="img" и aria-label; для кнопки с иконкой
  доступное имя задавать самой кнопке, а иконку оставлять декоративной.
- Для внутренних переходов использовать RouterLink.
- Для действий использовать button, для переходов — ссылки.
- Кнопкам только с иконкой задавать доступное название.
- ARIA задавать отдельными HTML-атрибутами (например, :aria-label,
  :aria-pressed, :aria-current), соответствующими роли и состоянию элемента.
- Не использовать Tailwind-варианты aria-* внутри class. Стили состояния
  задавать через :class или отдельные CSS-селекторы атрибутов.
- CSS-классы не заменяют ARIA-атрибуты. Проверять итоговые атрибуты в DOM;
  для компонентов Reka UI сохранять автоматически выставляемые ARIA-состояния.
- При проверке доступности опираться на W3C WAI-ARIA:
  https://www.w3.org/TR/wai-aria-1.2/.
- Сохранять видимый фокус и управление с клавиатуры.
- Не вкладывать кнопки и ссылки друг в друга.
- Для dropdown использовать готовый доступный компонент.

## Семантика HTML и ARIA

- Сначала использовать нативную HTML-семантику. Не добавлять role и ARIA,
  если нужное поведение уже выражено стандартным элементом.
- Структурировать страницу через main, nav, заголовки и смысловые секции.
  Для списков использовать ul/ol/li, для табличных данных — table.
- Связывать поля с видимыми label через for/id; группы полей — fieldset/legend.
- При наличии видимой подписи использовать её как доступное имя.
  Не подменять её несвязанным aria-label.
- ARIA-состояния должны отражать реальное поведение; ссылки в aria-controls
  и aria-labelledby должны указывать на существующие уникальные id.
- Не назначать aria-hidden="true" фокусируемым элементам и их контейнерам.
- Интерактивная роль требует соответствующего управления с клавиатуры.
  Предпочитать готовые доступные компоненты ручной имитации такого поведения.

## Адаптивная вёрстка

- Начинать с мобильной версии и расширять её через responsive-классы
  Tailwind: sm:, md:, lg:.
- Использовать flex, grid, гибкие размеры и max-width.
- Выбирать breakpoint по тому, где перестаёт помещаться содержимое.
- Не отслеживать ширину окна в JavaScript, если достаточно CSS.
- Проверять промежуточные ширины, а не только desktop и mobile.
- Проверять отсутствие горизонтального скролла и работу мобильного меню.

## Темы и локализация

- Использовать семантические токены: background, foreground,
  primary, muted, border и другие существующие цвета.
- Общую палитру задавать через CSS-переменные светлой и тёмной темы.
- Значения цветов задавать в формате oklch(), не HEX, RGB или HSL.
- Проверять читаемость, hover и focus в обеих темах.
- Использовать существующий vue-i18n и локали ru-RU / en-GB.
- Следовать принятому разделению общих и локальных переводов.
- Учитывать изменение длины текста при переключении языка.

## Команды и проверка результата

- bun run dev — локальный сервер.
- bun run typecheck — проверка типов.
- bun run lint — проверка ESLint.
- bun run build — проверка типов и production-сборка.
- bun run preview — просмотр собранного приложения.
- bun run test — однократный запуск unit-тестов через Vitest.
- bun run test:watch — тесты в режиме наблюдения.
- bun run test:coverage — тесты с покрытием через Istanbul и отчётом в coverage/.
- bun run test src/components/__tests__/PageHeader.test.ts — один файл тестов.

Использовать bun run test, а не bun test: последний запускает тестовый раннер Bun.

bun run build уже запускает typecheck.

В режиме обучения объяснять пользователю, какие проверки выполнить.
Не запускать автоисправление и другие изменяющие файлы команды
без разрешения на изменения.

После разрешённых правок выполнять проверки, соответствующие задаче.
Для изменений интерфейса дополнительно проверять его в браузере.

## Unit-тесты компонентов

- Не писать отдельные тесты для src/components/ui: это компоненты shadcn-vue.
  Проверять поведение собственных компонентов приложения, которые их используют.
  src/components/ui исключён из поиска тестов и отчёта покрытия.
- Не использовать jest-dom. Для утверждений использовать матчеры Vitest
  и нативные свойства и методы DOM (getAttribute, hasAttribute, disabled и т.д.).
- Использовать Vitest и @testing-library/vue; файлы называть *.test.ts
  и хранить в __tests__ рядом с компонентом.
- Импортировать describe, test, expect и vi явно из vitest.
- Для действий пользователя использовать userEvent.setup() и await.
- Все тестовые файлы и вспомогательный код хранить в локальных __tests__
  внутри соответствующих каталогов src, рядом с проверяемым кодом.
- Не создавать общий src/test, общий setup.ts и глобальный setupFiles.
  Подготовку окружения и cleanup() выполнять локально в тестах через
  beforeEach/afterEach. Cleanup выполнять перед восстановлением глобального состояния.
- Для stateful-плагинов, например router и i18n, создавать новый экземпляр
  на тест. Очищать изменённые хранилища и глобальное состояние после теста.
- jsdom не проверяет реальную вёрстку, размеры, CSS-breakpoints и перекрытия.
  Эти сценарии проверять отдельно в браузере.
- Проверять наблюдаемое поведение и реальные пользовательские сценарии,
  а не внутренние методы, структуру компонента или проценты coverage.
- Искать элементы по роли, доступному имени, label и видимому тексту,
  сначала ограничивая поиск смысловым контейнером.
- CSS-классы, глубокие селекторы и позиционные индексы использовать только
  при отсутствии устойчивого семантического способа поиска.
- Взаимодействовать с видимыми, доступными и готовыми элементами.
- Ждать наблюдаемого результата действия вместо фиксированных задержек.
- Изолированную логику проверять модульно, браузерные особенности SVG,
  фокуса, перекрытий и адаптивности — в реальном браузере.
- Тестовые фикстуры и вспомогательные функции размещать внутри локального __tests__.
- Начинать с проверок затронутого поведения; расширять прогон при наличии
  риска для связанных сценариев. Не добавлять искусственные тесты ради coverage.

Указывать, что проверено, какие ошибки обнаружены и что осталось
непроверенным. Не заявлять об успешной проверке без её выполнения.
